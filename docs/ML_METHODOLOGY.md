# Anomaly detection and ML methodology

Three supported comparators are deliberately kept separate:

**A. Threshold baseline.** A 5-second service window flags error rate over 0.20 or server span median latency above 500 ms (`threshold_anomalies`). These are configurable function arguments, not universally appropriate SLOs.

**B. Robust rolling statistical baseline.** For each service and metric (error rate, latency, throughput), compute median `m` and median absolute deviation `MAD` over up to 30 earlier windows. `z=(x-m)/max(1.4826*MAD, ε_metric)`, with floors `.035`, `10 ms`, and `.15 RPS`. Flag `|z|≥3.5` for enough previous samples (minimum 5 windows). Non-positive error-rate departures are ignored. No test windows enter their own baselines. This is a fixed heuristic; false-alert performance in production is unknown.

**C. Isolation Forest.** `causaltrace/ml.py` creates a real `scikit-learn` estimator with 150 trees on 3 features: error rate, latency and throughput. Training uses seeded healthy fixture `1001`; validation threshold selection uses seed `2002`; held-out test score uses seed `3003`. Tests do not train on labeled test rows. Model and JSON metadata are generated by `python scripts/train_ml.py`. The API's `GET /api/anomalies?method=ml` loads only the trusted, locally generated artifact and explicitly reports its synthetic training domain. Loading arbitrary untrusted pickle files is unsafe and not supported.

**Model choice:** No GNN or neural forecasting model is justified by current verified tests. The graph ranking is a deterministic, inspectable alternative, and Isolation Forest is a genuine fitted comparator, not a placeholder.

**Distribution warning:** Seeded fixture data are not realistic replicas of production metrics, nor of the true instrumented demo workload. Test metrics in `benchmarks/results.synthetic.json` are **synthetic fixture scores**, not claims of live lab detection. Recalibration on independent real baseline data is required before production use.
